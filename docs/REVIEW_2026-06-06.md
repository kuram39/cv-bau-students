## Alignment assessment

**Core assignment:** AI matching platform — extract CV data (personal, education, experience, skills, languages) → match candidates to job postings — with a student/fresh-grad fairness lens.

### ✅ Fully aligned

Every PR either tightens the extraction/matching quality or improves explainability and compliance. Nothing introduces a feature unrelated to the core pipeline:

- PRs #28, #33, #49 — evidence-tier system directly improves match *quality* (strong/medium/weak signal for how a skill was demonstrated vs merely listed). This is the conceptual heart of the student fairness angle.
- PRs #30, #31, #33 — classifier correctness fixes. Without correct candidate-type labelling, the recruiter's three-column view (students / changers / experienced) is meaningless.
- PRs #37, #38 — explainability + oversight. These are not scope creep; they are prerequisites for a real deployment (GDPR Art. 22, EU AI Act Annex III). The four-fifths audit and the override affordance are well-scoped.
- PRs #48, #51 — bridge_fit as months-to-ready and the threshold slider are UX improvements that make the existing score more graspable, not new axes.

### ⚠️ Minor observations (not flags)

1. **personal_fit retired but schema kept at 0.0** — correct decision, but the dead field in `MatchScore` and DB adds a small surface for confusion.
2. **single-target MVP** — the app is wired to one target ad (id 341). `find_candidate_ads` / `rank_candidate` exist for corpus search, but the pipeline always passes the target ad to the classifier. Fine for demo; worth noting if multi-role mode is needed.
3. **bridge_fit rubric covers 8 domains** — for roles outside these the UI shows `~N měs. + praxe` or N/A regardless of LLM quality. The saturation in the audit table is a parallel issue: 6 demo candidates → all pass → slider is the correct workaround (PR #51 addresses this well).

## Recommendations

### R1 — Vendor-tool alias table (highest ROI, no LLM needed)

`resolve_skill` measured at 21% layer-1 resolution. ESCO does not contain vendor
tools (`Power BI`, `Tableau`, `Looker`, `dbt`, `Jira`, etc.) which are the most
common hard-skills in Czech data-analyst ads. A curated 50–80 entry alias map:

```python
VENDOR_ALIASES = {
    "power bi": "data visualisation",   # ESCO 5af6abc...
    "tableau": "data visualisation",
    "dbt": "data transformation",
    "looker": "business intelligence",
    ...
}
```

Would close the single biggest resolution gap before any embeddings work.
Cost: ~2h. Branch: `feat/vendor-aliases`.

### R2 — Drop personal_fit from the DB schema (low risk, clean)

`personal_fit` has been `0.0` since PR #20. A single `ALTER TABLE matches
DROP COLUMN personal_fit` (+ matching SQLAlchemy model update + test fixtures)
would remove dead weight. This is the kind of cleanup that gets harder the more
prod data accumulates.

### R3 — Surface bridge_estimate on the candidate panel

The candidate panel currently only shows skill names for recourse
(`💡 Co doložit pro vyšší shodu`). The months estimate (`bridge_estimate`)
computed in PR #48 is available without extra LLM calls. Showing
`"doučení odhadem ~N měs."` on the candidate side provides a concrete next
step, consistent with Art. 86 AI Act candidate-facing explanation.

### R4 — Completion dialog in the UI (already in RISKS.md #5)

`completion/ask.py` generates follow-up questions but the recruiter/candidate
loop has no UI component to answer them. The pipeline stores them in
`CompletionRound` but they are invisible in the Streamlit UI. This is the
highest-value missing piece in the candidate journey. It would also justify
the `personal_fit` removal by replacing it with a structured questionnaire
score.

### R5 — Retry/back-off in llm.call_json (RISKS.md #4)

Rate-limit 429s from Anthropic Tier 1 (50 RPM) have no retry today. A simple
exponential back-off wrapper in `llm.py` would prevent upload failures during
any demo with multiple simultaneous uploads.

```python
# in llm.call_json: wrap the API call with tenacity
@retry(stop=stop_after_attempt(3), wait=wait_exponential(min=2, max=10),
       retry=retry_if_exception_type(RateLimitError))
```

### R6 — Integration smoke test (CI gap)

All tests are unit tests with mocked LLM. There is no smoke test that loads a
real CV file through `run_generic_pass` against an in-memory DB with a seeded
taxonomy. Even a mocked-LLM end-to-end test that checks the pipeline doesn't
crash on a minimal seed would catch the class of bug that caused the Neon boot
crash in PR #50.
