## Open risks (carried forward + new)

### 1. LLM cost — still 8 calls/applicant [HIGH, deferred]
`perf/llm-cost` not started. At Sonnet 4.6 pricing (~$3/MTok input), 8 calls × ~2k-token average ≈ $0.05/candidate. Negligible for a demo; painful at 10k CVs/month. The plan is in `docs/RISKS.md`; it just needs a branch.

### 2. Czech resolution coverage unknown [MEDIUM, gated]
`scripts/measure_resolution.py` was added in #36 but never run. The ESCO Czech-alias decision and embedding work are both gated on this number. Run it once against the demo seed; any result < 60% warrants immediate alias or embedding work before any production rollout.

### 3. Demo locked to one role [MEDIUM]
Seed was shrunk to data-analyst only (#24). The system claims universal ESCO coverage (14k skills, 6k occupations), but only ISCO 2511 has been validated end-to-end. A second role (e.g. HR manager ISCO 1212, IT support tech ISCO 3514) would stress-test the role resolver, evidence classifier, and bridge_fit generalization without touching the pipeline code.

### 4. Evidence tier boundary cases still being refined [LOW, ongoing]
PRs #28, #33, #49 show progressive refinement of the tier mapping (work, internship, thesis, brigáda, hobby, claimed). The tiering logic is the "fair comparison" claim's foundation. Unpaid internship / bootcamp project / part-time student job are not explicitly covered in the current logic. Worth adding a fixture table of edge-case CV snippets → expected tier assertions.

### 5. Candidate receives recourse but no decision signal [LOW]
PR #37 shows the candidate "💡 Co doložit" without knowing if they passed or failed the threshold. PR #38 added `match.recruiter_override` + `decision_at`. The infrastructure to surface "Váš profil je ve hře / nebyl vybrán" is already there but the candidate panel does not use it. After a recruiter makes an override decision, the candidate could receive a status (not the score — just pass/fail).

### 6. Postgres migration is one-way, no documented backup strategy [LOW]
The `--truncate` flag in `migrate_sqlite_to_postgres.py` wipes the target before pouring. If Neon credentials rotate or the free tier lapses, the owner must re-run from local SQLite. A `pg_dump` step in `DEPLOY.md` would close this gap with one line.

### Architecture / concept direction

The current architecture is a well-structured single-tenant demo. If the concept moves toward a multi-tenant recruiter SaaS:

- The `single_target_ad()` pattern in `bootstrap.py` needs to become a per-recruiter-session concept.
- Postgres already supports multi-tenant (add a `tenant_id` FK if needed).
- `audit_by_type()` output should be per-ad, not global (already the case — `ad_id` param; good).
- The `reasoning_cache` table is per-candidate, not per-candidate×ad — fine for single-target, will need a composite key for multi-ad.

No code changes recommended now (single-tenant demo is the right scope), but worth noting if the project pivots.
