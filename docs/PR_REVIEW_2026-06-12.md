## Alignment with core assignment

Core assignment: AI matching platform that processes CVs (extraction of
personal data, education, work experience, skills, languages) and matches
candidates to job postings — specifically making students / fresh-graduates /
career-changers comparable to experienced hires.

### All 20 PRs: ON TARGET — no scope creep detected

Every PR directly serves the matching pipeline or its correctness:

**Extraction / classification layer (#30, #31, #33)**
- Candidate-type classifier now fires relative to the actual job ad, not a
  self-stated target domain that was almost always empty. This is the right
  design for a single-target app and closes the "everyone defaults to
  experienced" bug.
- `real_work_years` separates brigáda (0.3×) from real employment for the
  2-year experience threshold — prevents inflation by seasonal work.

**Matching quality (#28, #33, #49)**
- `evidence.py` tier ladder (work/internship/open_source/cert → strong;
  thesis/project/course → medium; brigáda/hobby/other → weak) is the
  correct domain primitive. PR #49 fixed the critical bug where real
  employment defaulted to `other` → weak, making experienced candidates
  appear no stronger than hobby projects.
- Strongest tier wins when multiple capabilities resolve to the same skill id.
- Fallback-matched skills (via `esco_term`/`skill` rather than `skill_id`)
  now carry their evidence tier.

**Transparency / compliance (#37, #38)**
- Counterfactual recourse (`counterfactual_lifts`) is the correct GDPR
  Art. 22 / CJEU C-203/22 artifact: deterministic, zero-LLM, shows exactly
  which missing skills would improve the coverage score and by how much.
- Human-override affordance + recruiter note satisfies EU AI Act Art. 14
  human-in-the-loop requirement for high-risk AI systems.
- Bias-audit by candidate type with four-fifths ratio gives the recruiter
  operational visibility without requiring protected attributes.

**UX / presentation (#44, #48, #51)**
- Drill-in reorder (verdict first, answers last) matches recruiter
  decision flow: score → evidence → AI reasoning → candidate's own words.
- Bridge_fit as months-to-ready is more actionable than an abstract 0–100
  index; a recruiter can say "needs ~6 months upskilling" rather than "70".
- Threshold slider for the audit exposes saturation: if everyone scores
  above 50% the threshold needs raising, which is the correct insight.

**Operations (#29, #34, #45, #50)**
- Bootstrap correctly skips the 481-ad overlay when the scoped seed already
  provides the target ad — prevents wiping the prepared ApexFinance ad.
- Postgres `ADD COLUMN IF NOT EXISTS` idempotency fix is a genuine
  production-safety improvement; a single-tx-per-ALTER pattern is correct.

## Flags and risks

### FLAG 1 — `personal_fit = 0.0` tech debt (low severity, concrete plan needed)

`personal_fit` was retired after PR #20 but the schema column is kept as a
permanent `0.0`. Every `MatchScore` carries a dead field, and future readers
of `score.py` will wonder why it's there. The comment says "remove after a
DB migration cycle" — that cycle has not been scheduled.

**Recommendation:** Add a `chore/remove-personal-fit` entry to RISKS.md with
a concrete migration plan (e.g., `ALTER TABLE matches DROP COLUMN personal_fit`
once Neon is confirmed stable). Do not let it drift past the next major
schema version.

### FLAG 2 — bridge_fit rubric coverage: only `data-analyst` has a checklist

`bridge_plan` and `checklist_exists` only work for `(domain="data-analyst",
level)` tuples. Every other job ad — software developer, accountant, any other
domain — returns `bridge_fit = N/A`. In the single-target demo this is
invisible, but it means the platform cannot generalize beyond the demo without
new rubric content.

**Recommendation:** Either (a) add one or two more domain rubrics before
calling the platform "multi-role", or (b) document in RISKS.md that
bridge_fit is demo-only and will always be N/A for non-data-analyst ads.
The current state is honest (`N/A` shown, not a false number) but silent
about the limitation.

### FLAG 3 — Bias-audit label vs LL144 accuracy

PR #38 mentions NYC Local Law 144 to motivate the bias-audit feature, but
LL144 requires auditing by **race and sex** — protected demographic
attributes. The shipped audit audits by `candidate_type`
(student/career_changer/experienced), which is an operational category, not
a protected characteristic.

This is not a bug in the code — the audit is correctly scoped and the
MODEL_CARD documents "no demographic data." The risk is if the feature is
*presented* as LL144 compliance. It is not. It is useful for operational
fairness monitoring within the three candidate buckets.

**Recommendation:** In the recruiter panel and MODEL_CARD, label this
"operationele audit (kandidaatstype)" rather than "bias audit." Reserve the
term "bias audit" for when / if protected attributes are collected. Update
the LL144 reference in the PR description context to avoid future confusion.

### FLAG 4 — Czech resolution gap: measurement script exists, results not committed

`scripts/measure_resolution.py` was added in PR #36 specifically to quantify
the ~33% unresolved-skill gap before deciding whether to invest in ESCO Czech
aliases or embeddings. The script exists; the measurement has not been run
against the real DB and the results are not committed.

This means the gateway condition for the Czech resolution work is open but
no one has walked through it. The RISKS.md still says "~33% — inferred."

**Recommendation:** Run `measure_resolution.py` against the Neon DB (or the
demo DB), commit the output as `docs/resolution_baseline_2026-06.txt`, and
update RISKS.md with the real number. This is a 5-minute task that
gates a potentially significant engineering decision.

### FLAG 5 — Binary git bloat from seed rebakes

`data/seed.sqlite.gz` (9.2 MB) is committed to git. PR #34 rebaked it, and
PR #49 rebaked it again. Each rebake creates a new 9.2 MB blob in git history
that is never freed. After 10 rebakes: ~90 MB of hidden binary history.

**Recommendation:** Use `git lfs` for `*.sqlite.gz` or document in CONTRIBUTING
that seed rebakes should use `git commit --amend` (if not yet pushed) rather
than a new commit, or accept the bloat and schedule an occasional `git
filter-repo` cleanup. For a private repo with one contributor this is low
priority, but worth noting now.

### FLAG 6 — Dual-language docs maintenance burden

PRs #46 and #47 create a Czech primary README and a Czech ARCHITECTURE.md.
Both are good for the Czech-audience presentation. The risk: every future
code change that affects the documented architecture now needs two doc updates.

**Recommendation:** Add a note to CONTRIBUTING.md that the Czech docs are
"presentation snapshots" pinned to the current demo state, and are NOT
expected to be kept in sync with every future PR. When the architecture
stabilises, do a single catch-up translation rather than continuous dual
maintenance.
