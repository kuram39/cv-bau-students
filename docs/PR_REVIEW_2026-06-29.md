## Flags and risks (not blocking, but worth tracking)

### 1. High velocity → debt accumulation risk
45 PRs in 3 calendar days. Even with ~200 tests, fast-merged PRs accumulate
subtle interactions. The `_migrate_columns` crash (#50, fixed same day) is a
signal: Postgres-specific paths need their own CI path, not just SQLite in-memory
tests.

**Recommendation:** add a Postgres smoke-test job to `.github/workflows/ci.yml`
using a service container (`postgres:15`) so `_migrate_columns` / dialect-agnostic
upserts are actually exercised in CI, not discovered on boot.

### 2. Seed fragility (3 rebake PRs: #23, #34, + implicit in #45)
Every time a prompt or schema changes the seed needs a manual LLM-driven reseed
(owner key required) followed by `build_cloud_seed.py`. The bundled
`seed.sqlite.gz` is checked into git — this is correct for cold-start, but it
means CI cannot verify the seed is consistent with the current schema without
running it.

**Recommendation:** add a lightweight `tests/test_seed_integrity.py` that unpacks
the committed gzip, runs `init_db()` against it (no migration), and asserts the
expected table/row counts haven't regressed. This catches schema drift before the
next cloud deploy.

### 3. ESCO skill resolution coverage — number still unknown in CI
`scripts/measure_resolution.py` was written in #36 and is the correct instrument.
The runtime ESCO coverage for the 6 demo CVs is ~38% (from the PR body: "18/47
capability rows"). That number needs to improve before the platform handles real
CV uploads at scale — half the extracted skills will silently score 0 against
curated ESCO target sets.

**Recommendation (priority):** run `measure_resolution.py` on a fresh seed and
record the baseline in `docs/RISKS.md` item #21. Then tackle the cheapest fix
first: load ESCO hidden labels (`hiddenLabel` column in the ESCO skills CSV) —
one loader script, no embeddings, likely +10–15% coverage.

### 4. perf/llm-cost branch is still deferred (8 → 4 LLM calls)
Documented in `docs/RISKS.md` and `docs/research/07-llm-cost-latency.md` but not
started. Each CV upload still costs ~8 LLM round-trips. At Sonnet 4.6 pricing this
is manageable for a demo but will be the first pushback in a real deployment.

**Recommendation:** open the `perf/llm-cost` branch. The two easiest wins that
require no architectural change:
- Combine extraction + classification into one structured-output call (saves 1-2
  calls).
- Move the `explain` call to lazy/on-demand (recruiter clicks the drill-in expander)
  rather than running it at submit time.

### 5. Streamlit single-process concurrency (RISKS Tier 1 #2)
Still unaddressed. Two concurrent uploads serialize at the GIL + SQLite level.
Postgres is now wired (#16) but Streamlit's threading model means the 90s LLM
call still blocks the session. For the demo this is fine. For a real pilot it is
the first failure mode.

**Recommendation:** document the concurrency limit in the Streamlit UI itself (a
small info box: "Analýza trvá ~90 s; pro více souběžných nahraní kontaktujte …").
This sets expectations and defers the FastAPI/Celery rewrite to when it's actually
needed.

### 6. evidence 'work' tier bug (#49) indicates test gap
The bug — experienced candidates showing "doloženost: nízká" because real
employment mapped to the `other` source type — existed in production until caught
manually. The fix + backfill script are correct. But this class of bug (new
`source_type` value omitted from the tier map) should have been caught by an
evidence-tier exhaustiveness test.

**Recommendation:** add a parametrize test that asserts every `SourceType` member
maps to a tier in `evidence._TIER` — a one-liner that would have caught #49
before merge.

## Current state summary

The concept is fully intact and well-executed. The pipeline — CV upload →
personal data + skills extraction → ESCO resolution → candidate-type classifier
→ recruiter-curated scoring → drill-in with counterfactual recourse — is
coherent, tested, and cloud-deployed. Compliance features (human override,
bias-audit disclosure, confidence warnings) are proportionate and correctly
framed as disclosure tools rather than automated gatekeepers.

The main risks going forward are infrastructure (Postgres in CI, seed integrity)
and quality (ESCO resolution coverage, LLM cost per upload). None of these
threatens the core concept; they are the normal maturation path for an MVP
promoted to pilot.

1. `fix/esco-hidden-labels` — load `hiddenLabel` from the ESCO CSV → +10-15%
   resolution coverage, no LLM, no embeddings.

   caught before deploy.
