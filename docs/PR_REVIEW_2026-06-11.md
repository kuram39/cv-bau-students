## 2. Alignment with the core assignment

The core assignment is:
> AI matching platform that processes CVs (extraction: personal data, education,
> work experience, skills, languages) and matches candidates to job postings,
> adapted for students / fresh-grads / career-changers vs experienced-hire ads.

**Verdict: the concept is intact and has matured substantially.** Every major
feature group lands inside the brief. Specifics below.

### Fully aligned

- **CV extraction pipeline** (PR #5, #6, #10, #12) — candidate skills are
  normalised into the ESCO v1.2.x namespace; NSP Czech aliases layer on top;
  diacritics + phrase-qualifier stripping cover Czech input variability. The
  LLM translation step emits an English `esco_term` per capability that bridges
  the Czech→taxonomy gap without embeddings (justified in RISKS.md §Phase C).

- **Candidate-type classification** (PR #30, #31, #33) — the student /
  career_changer / experienced split is now **relative to the actual target ad**
  (domain/title match instead of self-stated intent). This is the right design
  choice: what constitutes "experience" only makes sense in context.

- **Evidence strength — doloženost** (PR #28, #49) — replacing the coarse LLM
  "spolehlivost" with a tier derived from `source_type` (work > internship/cert
  > thesis/project > brigáda/claim) is a significant quality improvement. PR #49
  closed the gap where real employment was mis-tiered as `other` → weak.

- **Counterfactual recourse + confidence caveat** (PR #37) — deterministic,
  zero-extra-LLM explanation of what a candidate would need to evidence to reach
  a higher coverage %. Directly implements GDPR Art. 22 / CJEU C-203/22
  "meaningful information about the logic" requirement. Well-scoped.

- **Human oversight + bias audit** (PR #38) — recruiter override, audit
  per-candidate-type selection rate, and four-fifths ratio disclosure. Correct
  scope for an EU AI Act high-risk tool. The implementation is disclosure-only
  (no demographic data → no LL144-style full audit), which is honest.

- **bridge_fit as months-to-ready** (PR #48) — converting the 0–100 index into
  a `~N měs.` estimate makes the "potential" axis immediately graspable for a
  recruiter. Small but high-value UX improvement.

### Aligned with deliberate trade-offs

- **Single-target MVP** (PR #20) — skills-coverage replaces the original 3-axis
  formula, and `personal_fit` is dropped (it was a weak lexical proxy). This is
  a sound simplification for a demo. The trade-off is documented; the multi-ad
  path (`rank_candidate → find_candidate_ads`) exists in the codebase but is not
  exercised in the current UI.

- **Role-scoped seed** (PR #24) — shrinking from ~200k to ~2k taxonomy rows for
  the single data-analyst demo is the right perf move. It does hard-code the
  scope to one domain. Switching roles requires a `build_scoped_seed.py` rebuild.

- **Postgres persistence** (PR #16, #50) — correct infra choice for Streamlit
  Cloud (ephemeral FS). The idempotent migration fix in #50 proves this path is
  in real use.

### No drift found

No PR introduces features outside the brief: no user-auth system, no payment
flows, no general LLM assistant, no unrelated ML models. The deep-research
reports (PR #35) are documentation, not code. The Czech docs (PR #46, #47) are
presentation artifacts for the local market, not product scope change.

## 3. Flags and risks

### Flag 1 — Single-target lock vs "matching platform" framing

The product description says "matching platform" but the current demo is pinned
to one ad (`job_ads.id = 341`, *Datový analytik* at ApexFinance). The corpus-side
code (`rank_candidate`, `find_candidate_ads`, SQL pre-filter) exists and is
tested, but it is bypassed by `pipeline._score_single_ad` in the current flow.

**Risk level: medium for a live product; low for the demo.**
The multi-ad path is already built; wiring it to the UI is a bounded task (see
Recommendation 1).

### Flag 2 — ESCO resolution gap (unquantified on live data)

RISKS.md §21 documents ~33% overall resolution on 6 demo CVs, with the
remaining 67% decomposed into vendor tools (~30%), soft traits (~37%), and
real hard-skill paraphrase (~33%). `scripts/measure_resolution.py` was shipped
in PR #36 but has not been run against the Neon production database.

**Risk level: medium.** If the demo runs only on the synthetic seed CVs the
gap is invisible. A real CV with many vendor tools (`Power BI`, `Tableau`,
`dbt`) could score near zero even if the candidate is a strong match, because
those skills fall outside ESCO. The recruiter skill-picker (manual add) is the
mitigation, but only if the recruiter knows to add them.

### Flag 3 — Evidence tier depends on LLM source_type classification

The doloženost system is correct given accurate `source_type` labels. But
`source_type` is LLM-extracted from the CV. PR #49 fixed one case where real
employment was classified `other`. The adversarial case — an internship
described in first-person work-like language being labelled `work` — is not
tested. A false-positive `work` label would inflate doloženost for a candidate
with no real employment.

**Risk level: low-medium.** The prompt now has explicit rules and a brigáda
exclusion. Adding reject-examples for the `work` tier (similar to the 6
existing skepticism examples) would close this.

### Flag 4 — 8 LLM calls per upload, not yet optimised

The documented `perf/llm-cost` branch (8→4 calls, defer reasoning + fold
translate) is still deferred. At demo scale (6 candidates) this is fine. At
~50 uploads/day it becomes ~$15/day on Sonnet. The optimisation is fully
designed in RISKS.md — it just needs a PR.

**Risk level: low now; medium at demo day if there is live upload volume.**

### Flag 5 — Corpus prefilter ignores curated target skills

Documented in RISKS.md as the last known gap: `rank_candidate`'s SQL prefilter
does not consult `ad_target_skills` (recruiter-curated ESCO ids). An ad that a
candidate matches *only* through its curated target skills can be filtered out
before scoring. This is a non-issue for the single-target demo but is a latent
bug for multi-ad use.

## 5. Recommendations

### Recommendation 1 (medium priority) — Wire multi-ad corpus path

The codebase already has `rank_candidate` → `find_candidate_ads` → `score_match`.
The UI's candidate panel calls `run_generic_pass(file, target_ad=…)` with a single
hardcoded ad. Adding a "Browse all ads" flow is ~50 lines: remove the single-ad
assumption in `pipeline.run_generic_pass`, let the candidate see the top-3 scored
matches, then `express_interest` on one. This is what the RISKS.md interview answer
calls out as "the path from demo to product." It does not require a schema change.

**Key gap to fix first:** `find_candidate_ads` prefilter ignores `ad_target_skills`
(documented in RISKS.md as the last known gap). Fix that JOIN before enabling
multi-ad UI to avoid silent misses.

### Recommendation 2 (quick win) — Add `work` tier reject-examples to the prompt

`prompts/translate_capabilities.md` has 6 skepticism reject-examples for capability
inflation. Adding 2–3 examples specifically for `source_type = work` (e.g., an
internship described as "worked at company X" that should remain `internship`, or a
semester project using work-like language) would guard against the false-positive
risk flagged above. This is a 15-minute prompt change with a test.

### Recommendation 3 (quick win) — Run `measure_resolution.py` on Neon data

```bash
python -m scripts.measure_resolution  # reads translated_capabilities from DB_URL
```

The result will either confirm the ~33% figure (then no action needed) or reveal a
worse gap that justifies loading ESCO Czech alt-labels. Decision gate: if overall
resolution < 25% after real uploads, load the ESCO Czech labels (scripts exist).

### Recommendation 4 (deferred, planned) — Execute `perf/llm-cost`

The design is fully in RISKS.md. The implementation is two changes: defer
`reason_for_ranking` until `express_interest`, and fold `translate` in
`submit_role_specific` into the existing profile summary. This is the right
next performance PR once the demo is stable.

### Recommendation 5 (architectural note) — Protect `candidate_type` at re-score

`rescore_ad(ad_id)` re-runs scoring for all candidates but does NOT re-classify
`candidate_type`. If a candidate was uploaded before PR #30 (classify vs target ad),
their type may be stale. A `reseed_types=True` flag on `rescore_ad` that re-runs
`classify(profile, target_ad=ad)` for each match would close this. Low risk for the
demo (all 6 seeds were rebaked post-#30), but worth a guard for live uploads.

### Recommendation 6 (ux note) — Clarify "student" label for career-changers

PR #31 correctly routes low-experience individuals into the `student` bucket.
However the UI label "student" may confuse a 35-year-old career re-entrant.
Consider renaming the bucket to "junior/potential" in the recruiter UI display
while keeping `candidate_type = "student"` in the DB enum — a one-line string
change in `recruiter_panel.py`.
