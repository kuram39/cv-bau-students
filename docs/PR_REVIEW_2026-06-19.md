## Flags and concerns

### F1 — Czech resolution gap: script exists, measurement hasn't landed

**Status: open risk, unmeasured**

`scripts/measure_resolution.py` (PR #36) was specifically added to measure
the actual ESCO resolution % before spending effort on Czech alias loading
or embeddings. That measurement hasn't been run and committed. The working
assumption of ~33% miss is still from 6 demo CVs (PR #9). With diverse real
CVs the number could be materially different.

**Recommendation**: Run `./venv/bin/python -m scripts.measure_resolution`
against a populated DB and commit the output to `docs/resolution_report.txt`.
That single number determines whether the Czech alias / diacritics work is
the right next investment.

### F2 — Role-scoped seed is a platform narrowing choice

**Status: deliberate, but constraining**

PR #24 scoped the seed to ~102 data-analyst-family skills. Cold-start is
now sub-second and the skill picker shows focused options. Trade-off: a
candidate skill outside the data-analyst family gets no ESCO id, and
switching the target role requires rebuilding the seed. The platform is
now a data-analyst demo, not a general multi-role matcher. This is the
right MVP scope, but "switching the target ad" is documented as a rebuild
operation — relevant if the owner wants to demo with different ads.

**Recommendation**: Keep the scoped approach but document `build_scoped_seed.py`
parameters clearly so the owner knows exactly what to change to target a
different role family.

### F3 — 6 demo candidates is too thin for meaningful bias audit

**Status: demo-correctness concern**

The audit added in #38 and improved in #51 requires enough candidates per
type to produce meaningful ratios. With 3 experienced + 2 student + 0 or 1
career_changer candidates, the four-fifths ratio will be 1.0 or undefined
at most sensible thresholds — saturated. The "saturation hint" from #51
helps, but a recruiter looking at the audit will see numbers that don't
demonstrate the feature's value.

**Recommendation**: Add 2–3 more synthetic career_changer CVs to the demo
seed so the audit has at least one candidate per bucket and a non-trivial
range of scores to split on. This is a seed/script change only, no code.

### F5 — `perf/llm-cost` branch still deferred

**Status: unchanged from prior review**

The 8→4 LLM call reduction is still unstarted. Research #7 shows the real
count is closer to 6 (ad-side calls already off the per-applicant path),
and the remaining calls are: extract_profile (fast), classify_candidate
(fast), translate_capabilities (think, slow), extract_role_answers (fast),
prefill_answers (fast), reason (think, slow). The two thinking calls
(`translate` + `reason`) account for most latency and cost.

**Recommendation**: The highest-ROI move is prompt caching on the `reason`
call — the system prompt is static per (ad, model), and `reasoning_cache`
already keying on `(candidate_id, ad_id, prompt_hash)` means the cache is
already being used but the Anthropic-level prompt-cache header isn't. Add
`"cache_control": {"type": "ephemeral"}` to the system prompt block in
`call_json` for `think=True` calls. Zero logic change, ~90% cost reduction
on cached calls.

### F6 — evidence tier for `work` (fixed in #49) may affect existing DB rows

**Status: requires owner action on production Neon DB**

PR #49 adds a `retag_work_evidence.py` script to backfill existing `other`
capabilities that came from work experience to the new `work` tier. The PR

`python -m scripts.retag_work_evidence --rescore-ad 341`." If this hasn't
been run on the Neon DB, experienced candidates still show incorrect
