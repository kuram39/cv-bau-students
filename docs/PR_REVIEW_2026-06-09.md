## Alignment with core assignment

Core assignment: AI matching platform that processes CVs (extraction of
personal data, education, work experience, skills, languages) and matches
candidates to job postings — specifically calibrated so students / fresh
graduates / career-changers are compared fairly against experienced hires.

### All 20 PRs: ON TARGET

Every PR either fixes the matching pipeline, improves CV processing accuracy,
enforces the student-vs-experienced distinction, hardens compliance, or
documents the system. Categorised:

**CV extraction / evidence quality (#28, #49, #33 partial)**
Direct improvements to how well the platform reads a CV. The `work` tier
fix (#49) was a genuine bug: a data analyst with 3 years of employment was
showing `doloženost: nízká` because job-derived capabilities were tagged
`other`. Fixing it is foundational to the fairness claim ("compare fairly").
Evidence-tier hardening in #28 makes the confidence signal meaningful rather
than uniform.

**Candidate classifier accuracy (#30, #31, #33 partial)**
The classifier now correctly separates: students, genuine career-changers
(by comparing work history against the target ad, not self-stated intent),
and experienced candidates. These labels drive the audit groups in #38 and
the separate recruiter column in the UI. Correctness here matters for the
whole platform.

**Compliance + explainability (#37, #38, #35 research)**
Counterfactual recourse (#37) and human override (#38) are the features an
HR-tech buyer will ask for first. They align exactly with the mission
(transparent AI matching, recruiter has final say). The four-fifths audit
(#38) is appropriately scoped as a disclosure metric, not a fairness guarantee
— consistent with the platform collecting no protected attributes.

**Demo / operational fixes (#29, #45, #50)**
Bootstrap flood (#29), bridge_fit N/A (#45), Postgres boot crash (#50) — all
three were silent blockers on the deployed demo. All correctly scoped.

**UX clarity (#44, #48, #51)**

view more actionable. The threshold slider (#51) turns a saturated disclosure
into a real signal.

**Docs (#32, #35, #36, #43, #46, #47)**

## Flags and recommendations

### R1 — `perf/llm-cost` branch: highest unbuilt ROI item ⚠️

**Status: still not started**

RISKS.md documents it precisely: `run_generic_pass` currently calls
`reason_for_ranking` on the top-3 matched ads **before** the user picks one.
Two of three reasoning calls are always wasted. Moving the reasoning to
`submit_role_specific` (which already does it for the selected ad) saves
≤3 LLM calls per CV upload with zero quality change.

The second saving (skip re-translate in `submit_role_specific`) is debatable —
the answer-blob fold may genuinely update the capability set — but the deferred
reasoning is unambiguously correct.

This is not cosmetic: at demo volume (6 CVs × 3 calls = 18 wasted calls) it
is noticeable. At any real scale it is the cost baseline.

**Recommended next branch:** `perf/llm-cost`.
Single change: move `reason_for_ranking(…, top_n=3)` out of `run_generic_pass`
and replace the preview cards with a deterministic "proč ti sedne" line
(skill-overlap count + bridge summary). The reasoning call in
`submit_role_specific` already handles the selected ad.

### R2 — Czech resolution % not re-measured after esco_term path ⚠️

**Status: tooling added (#36), measurement not done**

`scripts/measure_resolution.py` was added in #36 specifically to gate any
further Czech alias / embedding work. The last known number was 33% (from the
6 demo CVs, pre-LLM path). The LLM `esco_term` field in `TranslatedCapability`
was the designed fix for the cross-lingual gap — but no PR since #36 reports
the new number.

Running `measure_resolution.py` on the current demo DB (after the seed rebake
in #34 + #49) would give a current baseline. If esco_term-based resolution
brings the number above 60%, the Czech alias work in RISKS #21 can be deferred
further. If it's still below 40%, vendor tool aliases (Power BI, Tableau, Excel
— ~30% of the miss per RISKS.md) become the next action.

### R3 — Vendor tool aliases: highest-impact fix for student CVs ⚠️

**Status: documented in RISKS.md Tier 4 #21, not acted on**

Power BI, Tableau, Excel, pandas are absent or weakly represented in ESCO.
These are exactly the tools data-analyst student CVs list. They are ~30% of
the resolution miss for the demo CVs. A small, manually curated mapping file
(`data/vendor_aliases.csv`: tool name → ESCO skill id) fed into
`resolve_skill` would close this gap with no LLM, no infrastructure, and no
API dependency.

This has higher ROI than any other non-done item for the platform's target
population (students / fresh graduates in data-adjacent roles).
