## Concept integrity

The core assignment — AI platform that extracts capabilities from CVs (education,
projects, work, languages, skills) and matches candidates to job postings fairly
across student/changer/experienced types — is intact and has hardened substantially.

Key evolutions that are deliberate and sound:

- **Single-target MVP**: the app matches candidates against one curated job ad.
  Multi-target infrastructure (`rank_candidate → find_candidate_ads` SQL path)
  already exists in `matcher/rank.py`; the pivot to multi-target is a UI threading
  change, not an architecture rebuild.
- **`personal_fit` retired** (PR #20, before this window): skill coverage is the
  comparator. The axis was a weak lexical proxy and retiring it improves integrity.
- **Evidence tiers over LLM self-confidence**: source_type-based tiers (PR #28, #49)
  are more reliable and transparent than a coarse LLM confidence bucket.
- **GDPR / EU AI Act compliance baked in early** (#37, #38): counterfactual recourse +
  human-override + bias-audit log are the right answer for a high-risk-adjacent system,
  and adding them post-launch is painful. Good call.

## Issues and recommendations

### 1. Dead scoring code in config.py (low risk, medium confusion)

`WEIGHT_SKILL_FIT`, `WEIGHT_BRIDGE_FIT`, `WEIGHT_PERSONAL_FIT` are explicitly
marked `# UNUSED since PR #20` in `config.py:49–54`. They import-shadow nothing
(score.py uses `total = skill_fit` directly) but they mislead anyone reading the
file for the first time into thinking a weighted sum is somewhere.

**Recommendation**: remove the three WEIGHT constants from `config.py`. Update the
file header comment to say total = skill_fit (one axis). The `personal_fit=0.0`
hardcode in `score.py:77` can stay with its existing comment until the schema
field is formally migrated away.

### 2. Czech resolution gap — deferred but unquantified (medium risk)

`scripts/measure_resolution.py` was committed in PR #36 but the measurement has not
been run and the actual coverage % is unknown. The seed data is ESCO English +
Czech labels, but diacritics + alias mismatches during `resolve_skill` likely leave
a real gap. The CLAUDE.md open-items section calls this out but it's been deferred
through 20 PRs now.

**Recommendation**: run `./venv/bin/python -m scripts.measure_resolution` against
the demo DB (no API key needed, pure read). If Czech-subset resolution is below 60%,
prioritise the ESCO Czech alias load (`scripts/load_esco_hierarchy.py` already has
the infrastructure). Gate any demo for Czech-language CVs on this number.

### 3. Work evidence retag requires manual Neon step (ops risk)

PR #49 shipped `scripts/retag_work_evidence.py` to backfill existing DB rows where
real employment was incorrectly tagged `other` → weak tier. The script is
deterministic (no API key) but must be run manually on Neon:

```bash
python -m scripts.retag_work_evidence --rescore-ad 341
```

This is NOT in `docs/DEPLOY.md`. If the Neon instance is redeployed from the rebaked
seed (PR #34), it gets the corrected rows. If it was left running from before #49,
the retag is still needed.

**Recommendation**: add this one-time step to `docs/DEPLOY.md` under a "Post-merge
ops" section, or document it in the PR runbook. Verify Neon's `Markéta Horáková`
entry shows `doloženost: vysoká` to confirm the retag ran.

### 4. `counterfactual_lifts` shows identical delta for all missing skills (known, minor)

`score.py:173` computes `new_pct` as `round(100 * (evidenced + 1) / total)` — every
missing skill produces the same +N% uplift because each one adds exactly 1 to the
numerator. The code comment (`score.py:163`) documents this is deliberate ("kept
simple so swapping … is cheap"). Fair.

The UI currently renders "Doložit «X» → 50% → 56%", "Doložit «Y» → 50% → 56%", …
all with the same delta. This reads oddly to the recruiter — it looks like the system
can't distinguish which skill matters more.

**Recommendation** (optional, candidate-facing panel): consider ordering the
counterfactual list by the `source_type` most likely to close the gap fastest (e.g.
surface cert/course-bridgeable skills before experience-only ones), using data
already in `bridge_plan`. No score change needed — just ordering. Or keep as-is and
add a short note: "each of these adds ~N% coverage".

### 5. Audit saturation with thin demo (informational)

PR #51's threshold slider fixes the hard-coded 50% that saturated the demo (all 6
candidates passed). With only 2 candidates per type (student/changer/experienced),
the four-fifths ratio is statistically meaningless at any threshold. The UI already
calls this a "fairness-comparison aid, not a pass/fail bar" — that framing is
correct for the demo.

For any live deployment: the audit becomes meaningful only above ~10 candidates per
type. Document this floor in `docs/MODEL_CARD.md` (under "Known Limitations").

### 6. `LLM_THINK_MAX_TOKENS` naming (cosmetic)

`config.py:35–36`:
```python
LLM_THINK_MAX_TOKENS = 8000   # total budget (thinking + answer)
LLM_THINK_BUDGET = 4000       # thinking cap (leaves ≥4000 for answer)
```

The name `LLM_THINK_MAX_TOKENS` implies it's only the thinking budget, but it's
actually the `max_tokens` of the whole request. `llm.py` uses both; anyone who reads
the config first is likely to misinterpret `LLM_THINK_MAX_TOKENS` as the thinking
portion. Consider renaming to `LLM_THINK_REQUEST_MAX_TOKENS` or just adding a
one-line comment clarifying "this is max_tokens for the whole request, not just
the thinking block" in config.py.
