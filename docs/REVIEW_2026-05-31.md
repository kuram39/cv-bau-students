## New recommendations (R5–R9)

### R5 — `perf/llm-cost` is now the highest-priority next branch

Postgres shipping (#16) signals imminent Cloud production. At 8 LLM calls
per candidate on Sonnet 4.6 ($3/$15 per 1M i/o tokens), a 20-candidate demo
costs ~$0.40. Fine. But 100 real student uploads × 8 calls × ~2K tokens ≈
$2.40 with no queuing protection and Tier-1 rate limits. The 4-call optimisation
is already fully spec'd in `RISKS.md` (defer preview reasoning + fold second
`translate`). No quality loss. It should be the next branch.

### R6 — Recruiter skill-picker fallback needs a UI signal

When no recruiter has configured `ad_target_skills` for an ad, scoring falls
back to ISCO essential∪optional (~520 skills). Coverage reads `3/520` — an
uninterpretable number. `SkillFitDetail.target_source` already tracks
`'curated'` vs `'isco'`, but the Streamlit panel doesn't surface it.

Quick fix in `ui/recruiter_panel.py` (the skill-picker expander):
```python
if detail.target_source == "isco":
    st.info("Cílové dovednosti nebyly nastaveny — nastavte je výše pro smysluplné pokrytí.")
```
This single callout tells the recruiter what to do before they interpret scores.

### R7 — No end-to-end assembly test for the CV→match wiring

All 166 tests mock `llm.call_json`. Correct for CI speed, but the two-namespace
bug (#6 fix) was invisible to the suite until real data ran. The wiring
`esco_term → esco_skill_id → enrichment intersection` spans four modules and
has no integration smoke test.

Suggested: `tests/test_pipeline_smoke.py` — exercise `run_generic_pass` with a
known candidate dict + a single mock ad using a deterministic stub for LLM,
assert that `match.skill_fit_bonus > 0` when the profile contains a skill that
matches the ad's ISCO occupation. Not a live-LLM test; just an assembly check.

### R8 — `lru_cache` + loader mutation invariant (document, don't change)

`resolve_skill_esco` and `resolve_skill` are now module-level cached (process-
wide). Fine for Streamlit Cloud (single-process, read-only after seeding). The
risk is a post-load cache hit returning a pre-load result if `clear_resolution_caches()`
is called at the wrong moment.

Current implementation is correct: `clear_resolution_caches()` is called *after*
the last write in each loader, so a cache refill triggered mid-resolve can only
see the new data. Invariant to preserve: **always call `clear_resolution_caches()`
at the end of any function that mutates `skills` or `skill_aliases`**, not at the
start. A comment in `taxonomy/repo.py` would save the next editor.

### R9 — `psycopg2-binary` vs psycopg3 for Cloud deploy

`psycopg2-binary` has known compilation failures on Neon / Supabase + Python
3.12 (missing `libpq`). If a Streamlit Cloud build fails on it, the fix is:

```
# requirements.txt
psycopg[binary]>=3.1   # replaces psycopg2-binary
```
```python
# db.py — change dialect in DB_URL env var
# postgresql+psycopg://...  (psycopg3)
```

Not urgent until it actually breaks. Track: if `pip install psycopg2-binary`
fails in the deploy log, apply this.
