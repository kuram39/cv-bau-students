## New flags / concerns

### F6 — Czech skill resolution still unmeasured

**Status: open — deferred since last review**

`scripts/measure_resolution.py` was shipped in #36 but never run against real
data (no key needed; reads `translated_capabilities`). The inferred "~33% gap"
for Czech CV skills has not been verified, and no alias loading or embeddings
have been attempted. This is the single biggest quality gap for actual Czech CVs.

Recommendation: owner runs `measure_resolution.py` once against the demo DB
and records the output in a comment or `docs/` file. If resolution is below 50%,
the ESCO Czech alt-label loader is the next highest-ROI fix.

### F7 — `_migrate_columns` approach is fragile long-term

**Status: mitigated by #50, still present**

PR #50 made the ALTER TABLE migration idempotent (IF NOT EXISTS + per-ALTER
transactions). This is better, but the pattern of inferring schema changes from
SQLAlchemy model diffs at boot time is a footgun — the "stale reflection"
bug that caused the original crash can recur with more complex column changes
(type changes, renames, index additions). Alembic would eliminate this class
of bug.

Near-term: no action needed (the current fix is stable for the remaining columns).
Long-term: if the schema grows further, add Alembic before the next production
migration.

### F8 — Bias audit is not discriminating on the demo data

**Status: partially mitigated by #51**

The four-fifths audit produces meaningful output only when some candidates fail
the threshold. With 6 demo personas, even at 70% threshold everyone may pass —
making the audit table a row of 1.0s. PR #51's slider lets the recruiter explore
higher thresholds to find a discriminating cutoff, which is the correct approach.
But with 6 personas, "1 student fails at 80%" is not statistically meaningful.

The audit is correctly documented as a disclosure tool, not a decision metric.
For a real demo, loading 10–20 CVs (a mix of student/career_changer/experienced)
would make the audit tables legible. This is a demo-content issue, not a code bug.

### F9 — `LLM_THINK_ENABLED` env-var default flip breaks the speed demo toggle

**Status: low risk, note for owner**

F1 is fixed (thinking is on by default, correct). But the original intent of
the flag was a speed toggle for demos. Now that the default is on, a demo
operator who wants to suppress thinking to cut latency must set
`CV_BAU_STUDENTS_THINK=0` explicitly. This is not documented in the Streamlit
app or the Cloud deploy README. Worth a one-liner in `docs/DEPLOY.md`.

## Recommendations

The following are concrete recommendations for the next development cycle. They
are ordered by impact on the core mission.

### R1 — Run resolution measurement before anything else (no key, 5 min)

```bash
./venv/bin/python -m scripts.measure_resolution
```

The output tells you whether Czech CVs are being scored fairly or silently
mis-scored due to unresolved skills. Everything else (alias loading, embeddings,
LLM-cost work) is guesswork without this number.

### R2 — Load ESCO Czech alt-labels if resolution < 50% (gated on R1)

The ESCO distribution includes hidden/alt labels in Czech. Loading them into
`taxonomy_skills.cs_label` and `taxonomy_skill_aliases` would capture the
majority of diacritics and synonym misses without embeddings.
Estimated effort: 2–3h (extend `load_esco_csv.py`, rebuild seed).

### R3 — Haiku model-tiering for extraction calls (reduces cost 3×)

Research report #7 identified the 4 extraction/classification calls
(non-think) as candidates for `claude-haiku-4-5` downgrade. These are
deterministic JSON-structured tasks where Haiku performs comparably to Sonnet.
Add a `LLM_EXTRACTION_MODEL` constant (default Haiku) alongside the existing
`LLM_MODEL`. This is the largest remaining cost lever.

### R4 — Add 10–15 varied demo CVs for a meaningful audit

With 6 personas the bias-audit table is not legible. Synthetic CVs for 3
more student types (e.g., economics student, language student switching to
data, recent bootcamp grad) would make the audit discriminating and strengthen
the demo's core thesis about fairness across candidate types.
`scripts/generate_student_cvs.py` + `seed_target_demo` already handle this.

### R5 — Delete dead weight constants

```python
# config.py — remove these three lines (they are not read anywhere):
# WEIGHT_SKILL_FIT = 0.45
# WEIGHT_BRIDGE_FIT = 0.35
# WEIGHT_PERSONAL_FIT = 0.20
```

A reader who sees these constants assumes they drive the score. They don't —
`total = skill_fit` directly in `score.py`. Removing them removes ambiguity.
