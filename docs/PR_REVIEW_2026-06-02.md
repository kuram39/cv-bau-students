## 1. Concept alignment

**Verdict: fully intact.** The core assignment — AI matching platform for students /
fresh-grads / career-changers that translates non-traditional CVs into
experienced-equivalent capabilities and matches them against job ads — has not drifted.

### Architectural pivot in PR #20 (deliberate, not scope creep)

The scoring model changed from a 3-axis weighted formula (skill 45% + bridge 35% +
personal 20%) to a skills-coverage headline (`total == skill_fit`). This is a
clarifying simplification, not a contradiction: the original model's personal_fit axis
was a weak lexical proxy that produced no meaningful signal, and the multi-weight
scheme obscured what recruiters actually care about — whether the candidate's skills
cover the target set. The change makes the score more comparable across student vs
experienced profiles, which is precisely the platform's stated goal.

`bridge_fit` is retained as a secondary "potential/growth" signal rather than a
headline contributor. It answers a different question ("how bridgeable are the gaps")
and should stay separate.

### Single-target MVP scope (PR #20, #24)

The seed and bootstrap are now scoped to one data-analyst role. This is an explicit
design choice (documented in the README and DEPLOY.md), not an accidental narrowing.
The codebase is architected so that swapping the target ad and rebuilding the scoped
seed is a single-operator operation. No architectural obstacle to going multi-role.

## 2. Quality and engineering highlights

**PR #28 evidence-strength system** is the most significant quality improvement in
this batch. Replacing coarse LLM self-confidence ("střední for everyone") with a
structured `source_type → tier` ladder (work/internship/cert → 🟢; thesis/project/
course → 🟡; brigáda/hobby/claimed → ⚪) is correct and research-backed. Recruiters
now see HOW a skill was demonstrated, not just IF it was claimed.

**PR #30–#31 classifier fixes** close a real correctness gap: the old catch-all
"experienced" bucket incorrectly labelled gap-year re-entrants, low-work-history
candidates, and brigáda-only histories as experienced. The fix (real_work_years <
STUDENT_MAX_WORK_YEARS → student) correctly routes them to the potential-based column.

**PR #24 scoped seed** cuts cold-start time from ~10s (200k rows) to sub-second
(~1.1k rows). Correct performance decision for a demo-sized single-target system.
The scoring is verified unchanged (same 5 scores before/after).

## 4. Issues found and fixes committed (this branch)

### BUG (fixed): missing `"work"` source_type — professional work scored as "weak"

**Root cause**: PR #28 introduced the `source_type → tier` evidence ladder. The
`SourceType` literal (`models.py`) and the translator prompt never had a `"work"` type
for regular full-time / part-time professional jobs (non-internship). The LLM therefore
assigned `source_type: "other"` for work experience entries, which maps to tier `"weak"`
(⚪ "jen uvedeno").

**Impact**: An experienced data analyst with 5 years of professional SQL work received
the same evidence tier as a hobby-derived skill. Career-changer examples in the prompt
itself (Example B) used `source_type: "other"` for `work_experience` rows. The
evidence-strength display was correct in concept but incorrect in practice for all
non-internship professional experience.

**Fix applied in this commit**:
- `models.py`: added `"work"` to `SourceType` literal
- `evidence.py`: added `"work": "strong"` to `_TIER` (with explanation comment)
- `translate_capabilities.md`: added `"work"` to the source_type enum in the JSON
  schema, added a calibration row to the table, updated Example B to use `"work"`

**After fix**: professional work experience → 🟢 "prokázané praxí" (same as
internship/open_source/certification). A re-score is needed on existing Match rows to
propagate the corrected tiers.

### STALE COMMENT (fixed): config.py thinking budget mismatch

The block comment above `LLM_THINK_MAX_TOKENS` said "12000 total = up to 8000 thinking
+ ≥4000 for the JSON" but the actual values are 8000 total / 4000 budget. PR #19
reduced the budget after latency issues but the explanatory comment was not updated.
Fixed to accurately describe the current 8000/4000 split.

## 5. Open items (not fixed here, flagged for future branches)

### A. Diacritics strip in `resolve_skill` (pre-existing, from CLAUDE.md)

CV text "dulni nakladac" (without háčky) returns `None` from `resolve_skill` even
though "důlní nakladač" resolves correctly. The ESCO resolver strips diacritics at
index-build time but the query string is not normalized. One-line fix:
```python
# taxonomy/repo.py  resolve_skill()
term = _strip_diacritics(term.lower().strip())
```
Suggested branch: `fix/resolve-skill-diacritics`

### B. Remove `WEIGHT_*` dead constants

`WEIGHT_SKILL_FIT`, `WEIGHT_BRIDGE_FIT`, `WEIGHT_PERSONAL_FIT` in `config.py` are
annotated UNUSED since PR #20 but still live in the file. Remove them in a cleanup
pass once confident no downstream code references them (grep confirms none currently
do). Suggested branch: `chore/cleanup-dead-weights`

### C. `personal_fit` schema field retirement

`MatchScore.personal_fit` is hard-coded to `0.0`. The field should be removed after a
DB migration cycle (drop column from `matches` table). Currently deferred correctly.
Suggested branch: `chore/drop-personal-fit`

### D. `confidence_band` signal now partially redundant

`_confidence_band` derives a `±` uncertainty range from the LLM's self-confidence
floats. Since PR #28 the display-facing reliability signal is `doloženost` (evidence
tier). The confidence band is a different concept (score uncertainty, not evidence
quality) but its use in the UI and the definition of "what it means" should be
revisited — it may cause confusion for recruiters who now have two reliability
indicators. No urgency, but worth a design decision.

## 6. Current project state

**Concept: intact and sharpened.** The platform correctly:
- Extracts profile data from CV text (name, education, work, skills, languages)
- Classifies candidate type relative to the target ad (student / career_changer / experienced)
- Translates non-traditional experience into ESCO-anchored capabilities with evidence quotes
- Scores against a recruiter-curated target skill set
- Surfaces evidence strength per matched skill (doloženost)
- Persists candidates across sessions (Postgres/Neon)
- Presents a two-panel Streamlit UI (candidate journey + recruiter scored list)

**New directions that are sound**:
- Evidence-strength tiers (PR #28): moves reliability signal from "LLM says so" to
  structured provenance — correct direction.
- Classify-vs-ad (PR #30): removes the self-stated `target_domains` dependency that
  made career_changer rarely fire — correct fix for a single-target app.

**No architectural risks detected.** The single-target constraint is the only design
choice that limits generalizability, and it is intentional and documented.
