## Flags / Known Issues

### FLAG-1 — `personal_fit` field is technical debt (zero forever)

Removed from scoring in PR #20 ("weak lexical proxy") with note "remove after
a DB migration cycle." That cycle has not happened. The field is a permanent
`0.0` in every `MatchScore`, `Match` DB row, and any CSV export, misleading
any schema reader.

**Recommendation:** schedule a single `ALTER TABLE … DROP COLUMN personal_fit`
migration + remove the field from `MatchScore`, `db_models.Match`, and
`score_match`. No data is lost — the field carries no information. A DB backup
before the ALTER is sufficient risk mitigation.

### FLAG-2 — `counterfactual_lifts` items are interchangeable (UX risk)

`counterfactual_lifts` in `matcher/score.py:148` returns up to 5 missing
skills, each showing the same "current%→new%" because adding any one skill
always moves the numerator by exactly 1. The list *looks* ranked but is not.

**Recommendation:** either (a) add a short note in the UI that all items carry
equal weight, or (b) break the symmetry by weighting essential > optional
skills (already separated in `SkillFitDetail.missing_must` vs implicit optional
gap) so the top item genuinely is "highest-priority skill to demonstrate."
Option (a) is a one-line UI change; option (b) is a scoring change.

### FLAG-3 — `measure_resolution.py` has never been run

PR #36 added `scripts/measure_resolution.py`. CLAUDE.md explicitly gates the
embeddings / Czech-alias work on this number. The Czech ESCO resolution rate is
still unknown.

**Recommendation:** owner runs `python -m scripts.measure_resolution` against
the seeded DB (no LLM key needed). If resolution < 60%, prioritise the Czech
alias load. If ≥ 80%, the lexical + diacritics fallback is sufficient and
embeddings can stay deferred indefinitely.

### FLAG-4 — Single-target limitation is invisible in the UI

The MVP compares all CVs against one fixed ad. No in-app message says this.
A recruiter landing on the tool without a demo briefing will not know this.

**Recommendation:** add a one-line info banner in `recruiter_panel.py` beneath
the ad header: "Tato verze vyhodnocuje kandidáty vůči jednomu předvybranému
inzerátu." Small change, prevents expectation mismatch.

### FLAG-5 — `_bridge_fit` scale ceiling is arbitrary and uncommented

`matcher/score.py:243`: `100 - (total_months / 24.0) * 100`. The 24-month
ceiling has no documented rationale. A candidate with a 30-month bridge plan
gets a negative value before the `max(0, …)` clamp, collapsing them with the
"experience-only wall" case (35.0 cap) in terms of display.

**Recommendation:** add a comment explaining the 24-month assumption, or move
the ceiling to `config.py` (`BRIDGE_FIT_CEILING_MONTHS = 24`) so it is
adjustable without hunting through score.py. Also consider whether the
"experience-only wall" case (35.0) should be 0 rather than 35 — currently a
candidate who needs 23 months of courses (score ≈ 4) scores worse than one who
needs an experience-only year (35).

## Concept Recommendations

### REC-1 — Run `rescore_ad` after every evidence-model change

PRs #28, #33, #49 all added `# After merge: run rescore_ad on Neon` notes but
these are easy to miss. Consider adding a one-line entry to `scripts/README.md`
or `CLAUDE.md` listing which DB operations must be run after model changes, so
the maintenance checklist is explicit.

### REC-2 — Promote `bridge_fit`'s months-to-ready to the candidate panel

The recruiter sees "~N měs. doučení" (PR #48). The candidate only sees skill
coverage and bare recourse lines. The months-to-ready is also useful to the
candidate — it is career advice, not scoring. Showing it on the candidate side
(without the score) aligns with EU AI Act Art. 86 (meaningful information on
automated processing) and makes the tool more actionable for the candidate.

### REC-3 — LLM cost path: prioritise the `perf/llm-cost` branch

8 LLM calls/CV is the main scaling blocker and the main cost risk. The roadmap
says 8→4 calls. Based on the current call structure (extract_profile,
translate_capabilities ×N, classify, reason_explanation, ask_role_questions):
the two biggest wins are (a) batch-translate all capabilities in one call
instead of per-source-type calls, and (b) make `reason_explanation` lazy
(generate only when a recruiter opens the drill-in, not at upload). Together
these likely get to 3–4 calls with no accuracy regression.

### REC-4 — Archive deep-research docs into a collapsible structure

`docs/research/` now has 8 reports. They are valuable reference material but
they dominate the docs directory and slow down navigation. Move them to
`docs/research/` (already done) and add a one-paragraph `docs/research/README.md`
index so they are findable without opening each file.
