## 3. Findings and recommendations

### 3.1 Dead code: `personal_fit` schema field

`models.MatchScore.personal_fit` is set to `0.0` everywhere since PR #20 retired the
axis. The comment in `score.py:10` says "remove after a DB migration cycle". That cycle
never happened, and the field has now appeared in 30+ commits of read paths.

**Recommendation:** File a `chore/remove-personal-fit` branch. The migration is trivial
(`ALTER TABLE matches DROP COLUMN personal_fit` on Postgres; the column is 0.0 in every
row). The schema field adds noise to every `MatchScore` repr and every JSON blob stored
in `Match.score_json`. Low risk, clean-up value is high.

### 3.2 Dead code: legacy `analyze_candidate()` in pipeline.py

`pipeline.analyze_candidate()` is kept for "back-compat with the original single-page
UI + tests". The two-pass journey (`run_generic_pass → express_interest →
submit_role_specific`) has been the primary path since Phase 12. If the original UI tab
no longer exists, this is dead code carrying its own test surface.

**Recommendation:** Check which tests call `analyze_candidate()`. If it is only exercised
by tests — not any live UI path — remove it together with those tests and note the
deletion in the PR description. Reducing the orchestrator surface makes the codebase
easier to audit for new contributors.

### 3.3 `counterfactual_lifts` returns identical (current, new) for all missing skills

`matcher/score.py:148–174`: every missing skill generates the same `(current_pct, new_pct)`
pair because adding any single skill adds exactly 1 to the numerator. The UI renders
distinct lines ("Doložit «Python» → 50% → 55%", "Doložit «SQL» → 50% → 55%"), but both
percentages are identical for every row — the only varying element is the skill name.

This is acknowledged in the comment ("Kept deliberately simple so swapping in a plain
reason-codes list is cheap") but it can confuse a recruiter who reads the lines as if
each has a different marginal impact.

**Recommendation (low-effort):** Sort the recourse list so must-have gaps precede
nice-to-have gaps. Already feasible from `SkillFitDetail.missing_must` vs
`role_essential_missing`. This preserves the simple arithmetic while making the
ordering informative. A stretch option — still zero-LLM — is to annotate each skill
with its tier category ("must" / "nice") so the recruiter understands priority.

### 3.4 Czech skill resolution gap — quantify before spending effort

`scripts/measure_resolution.py` was added in PR #36 specifically to measure what % of
candidate skills resolve against the ESCO taxonomy. The CLAUDE.md notes the "inferred
~33%" gap from research. That script has not been run since the seed was rebaked in
PR #49 (work evidence) and the classifier was improved in PRs #30–33.

**Recommendation:** Owner should run `measure_resolution.py` against the current seed
before opening any `perf/czech-resolution` branch. The real number may be much better
than 33% now that the classifier correctly separates brigáda-only profiles from
experienced ones (inflated `total_work_years` previously could push non-data skills into
the resolved set, masking the real coverage). Measure first, improve only if the number
warrants it.

### 3.5 Audit saturation persists even with the new threshold slider (#51)

The bias audit (PR #38, slider in PR #51) computes per-type selection rates at the
chosen threshold. With only 6 demo candidates (3 data-analyst students + 3 experienced)
who all score relatively high, the audit will saturate at any reasonable threshold.
The PR body acknowledges this and adds a saturation hint ("everyone passes → raise the
threshold"). But the hint does not help if the groups are not balanced or if all
candidates clear even a high threshold.

**Recommendation:** The clearest demo fix is adding at least one "weak" candidate per
group — a low-skill student, a weak career-changer — to populate the low end of the
score distribution and make the four-fifths ratio non-trivial. These can be synthetic
CVs in `data/raw_cv_samples/`. Without this, the audit page remains an illustration
of the feature rather than a live demonstration.

### 3.6 Minor: `_DOMAIN_MATCH_THRESHOLD = 85` in classify.py may be fragile on short strings

`rapidfuzz.fuzz.partial_ratio` with a threshold of 85 against short ad `domain` slugs
(e.g. "data-analyst", 11 chars) can produce unexpected matches on unrelated short
tokens because partial_ratio aligns the shorter string within the longer one. A domain
slug of "hr" would match almost any longer string containing "hr".

**Recommendation:** Add a minimum-length guard before the fuzzy comparison:
if `min(len(t), len(af)) < 5: continue`. Low risk to existing behaviour (current ad
domain is "data-analyst", 11 chars) but important if more diverse ads are added.
