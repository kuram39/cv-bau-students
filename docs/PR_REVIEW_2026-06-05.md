## 3. Flags — drift risks and concerns

### Flag A — `personal_fit` dead code (low severity)
`score.py:8` documents that personal_fit was retired after PR #20.
The column is still stored as `0.0`, and the schema field `Match.personal_fit` still
exists. No PR removed it. This is harmless today but will confuse future contributors.
**Recommendation:** one-PR cleanup — zero out in scorer (done), drop from `db_models`
in next migration cycle, remove from `MatchScore`.

### Flag B — `_auto_add_missing_columns` fragile migration pattern (medium severity)
`db.py` uses ad-hoc `ALTER TABLE … ADD COLUMN` on every boot.
PR #50 was a prod-down incident caused by this: Postgres inspector reflection
returned a stale column list, the guard was bypassed, and a duplicate-column ALTER
was issued on every restart.
The fix made the guard explicit, but the root cause remains: schema evolution is
managed by hand-coded ALTER strings rather than a migration tool.
**Recommendation:** introduce Alembic (it already supports both SQLite + Postgres)
on the `chore/alembic-migrations` branch. The existing `_auto_add_missing_columns`
stays as a safety net for zero-downtime deploys but is no longer the source of truth.

### Flag C — bias-audit slider abuse vector (low-medium severity)
PR #51 adds a threshold slider (0–100 %) to the recruiter audit so they can find
the selection threshold where the four-fifths disparate-impact ratio holds.
The intent is auditability — a legitimate EU AI Act concern.
Risk: a recruiter could use the slider in reverse — sweeping until they find a
threshold that passes the four-fifths test while still yielding the selection they
wanted. The audit becomes evidence of compliance without actually being constrained.
**Recommendation:** log the threshold chosen at decision time (already captured if
`decision_at` is set on override), and surface the audit read-only after the fact
rather than as a live slider before selection. Or: lock the threshold to the
industry-standard 80 % and make the slider expert-only behind a settings flag.

### Flag D — docs-heavy sprint (informational, no action required)
5 of the 12 PRs merged on 2026-06-02 are documentation only (#35, #36, #43, #46, #47).
This is not scope creep — the docs are accurate and valuable (ARCHITECTURE.md with
Mermaid diagrams is genuinely good). The Czech-primary README signals the intended
market (CZ) and doubles as a presentation script, which is appropriate.
Note: it does mean no new feature PRs landed on that day.

## 5. Code-level recommendations

### 5a. Retire personal_fit properly

In `src/cv_bau_students/matcher/score.py`, `personal_fit` is computed as `0.0` and
the comment says "remove after a DB migration cycle". To complete the retirement:

```python
# score.py — remove this entirely once db_models.Match.personal_fit is dropped:
# score.personal_fit = 0.0
```

In `db_models.py`, the `Match.personal_fit` column can be dropped in the next
ALTER cycle once all running instances have been migrated.

### 5b. Alembic bootstrap (one-time setup, ~30 min)

```bash
./venv/bin/pip install alembic
./venv/bin/alembic init alembic
# edit alembic/env.py: target_metadata = Base.metadata; url from config.DB_URL
./venv/bin/alembic revision --autogenerate -m "initial"
./venv/bin/alembic upgrade head
```

After this, every schema change gets a versioned migration file. Keep
`_auto_add_missing_columns` as a defensive boot-time check but stop adding new
columns through it.

### 5c. Batch `names_for_ids` to top-N only

RISKS.md §22 documents this: `skill_fit` resolves ESCO names for every ad in the
pre-filter pool before the top-N is kept. The fix is to score on IDs only and
resolve names only for the kept top-N (display layer). In `matcher/score.py`:

```python
# Current: names_for_ids called before rank
# Target:  score_match returns ids; recruiter_panel calls names_for_ids
#          on the top-N after rank.top_n() clips the pool
```

This is a pure refactor with no behaviour change — safe to do anytime.

### 5d. Request-level timeout + retry in llm.call_json

`llm.py` already has a 180 s timeout. RISKS.md §4 notes that Tier 1 rate-limit
(50 RPM) will hit with 9+ concurrent uploads. The current code has no retry-with-
backoff on 429s. Add:

```python
import time

for attempt in range(3):
    try:
        return _client().messages.create(...)
    except anthropic.RateLimitError:
        if attempt == 2:
            raise
        time.sleep(2 ** attempt)  # 1s, 2s
```

This is the quick fix noted in RISKS.md; it unblocks small demos without a queue.

## 6. Current state summary

**Concept: intact.**
The platform correctly implements its mandate: it translates student CVs (thesis,
courses, brigády, prior-domain achievements) into ESCO capability space, scores
them against job ads on skill coverage rather than years of experience, surfaces
a bridge-fit estimate (months to ready) as a growth signal, and gives recruiters
transparency (counterfactual recourse, evidence tiers, override audit).

**Maturity: demo-ready, not production-ready.**
The architecture is sound for the demo scenario (single data-analyst ad, ~10
candidates). The known production gaps (async pipeline, queue, observability, DPA)
are correctly documented and deferred.

**Pace: rapid but controlled.**
45 PRs in 5 days is fast. Code quality held: the test suite has 37 test files,
CI gates ruff + black + pytest, and each PR carried a clear "Why / What changed"
structure. No PRs merged with a red CI status.

**Biggest near-term risk: LLM cost.**
8 LLM calls per applicant at Sonnet 4.6 rates is ~$0.03–0.08 per upload. For a
10-candidate demo this is negligible. For a production batch of 200 CVs it's $6–16
per ad posting — non-trivial. The `perf/llm-cost` branch is the right next focus.
