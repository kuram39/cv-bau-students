education, work experience, skills, languages) and matches candidates to job
postings — with special handling for students / fresh-graduates / career-changers

## Risks & Issues

### R-1 — Role-scoped seed makes the system single-domain (HIGH)
PR #24 shrunk the DB from ~200k to ~2k rows by scoping seed to the
data-analyst ISCO occupation. This is correct for the demo, but it means the
system **cannot match against arbitrary job ads without a DB rebuild**. Any
ad outside data-analyst will resolve ESCO skills only against that subset.

**Recommendation:** Document this explicitly as a demo constraint in DEPLOY.md.
Add a `--full-seed` flag to `bootstrap.py` / `build_cloud_seed.py` that
restores full ESCO coverage. Before any second demo or investor review with a
different job, run full-seed first.

### R-2 — 8 LLM calls per applicant: unstarted perf branch (HIGH)
RISKS.md documents the 8→4 call reduction target. The `perf/llm-cost` branch
hasn't started. At 40 applicants (the demo seed), that's 320 LLM calls on
first run. At 400 applicants (a real HR queue), it's 3200 calls — cost and
latency become blockers.

**Recommendation:** Start the perf branch. The lowest-hanging fruit is caching
the extraction pass (CV text rarely changes) and combining the classify +
prefill calls. Target: 5 calls per new applicant, 1 on re-score.

### R-3 — Czech skill resolution coverage unknown (MEDIUM)
`scripts/measure_resolution.py` was added in #36 but never run and committed.
The diacritics fallback in `resolve_skill` is best-effort; we don't know what
% of Czech-named skills in real CVs actually resolve to ESCO IDs.

**Recommendation:** Run `measure_resolution.py` against the 6 demo CVs and
commit the output to `docs/resolution_coverage.txt`. If resolution is < 70%,
prioritize the Czech ESCO alias load (not embeddings — that's overkill until
we know the gap).

### R-4 — Audit threshold slider is a UI dead-end (LOW)
PR #51 adds a nice bias-audit slider, but:
- The threshold doesn't persist between sessions (session_state only).
- The audit result doesn't feed back into any workflow or decision.
- There's no guidance on what threshold is legally defensible.

As a fairness *exploration* tool it's fine. As an *accountability* tool it
needs: persisted threshold, a timestamp on the CSV export, and an explicit
label that this is a fairness check, not a hiring decision boundary.

### R-5 — personal_fit axis retired but not cleaned up (LOW)
PR #20 retired `personal_fit` (now hardcoded 0.0). The schema field exists,
the `MatchScore` dataclass carries it, and UI code may still render it. The
scoring is effectively 2-axis. Either:
(a) Drop the field in the next migration cycle, or
(b) Replace it with a real 3rd signal: motivation match from role-specific Q&A
    answers already collected in the pipeline.

Option (b) is better — the Q&A data exists, it just isn't scored.

### R-6 — bridge_fit shows N/A for any role without level checklists (LOW)
`bridge_estimate()` returns N/A when `checklist_exists()` is False for the
target ISCO. The demo works because data-analyst has checklists. Any other
ISCO won't. The recruiter panel shows "N/A" with no explanation.

**Recommendation:** Display "Žádná učební osnova pro tuto roli" (no learning
path data for this role) instead of a bare N/A, and note that bridge_fit
requires level checklists to be loaded for the target ISCO.
