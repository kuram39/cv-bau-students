## Recommendations

### Immediate (1–2 h, low risk)

**R1 — Fix diacritics in `resolve_skill` (seed-space resolver)**

`resolve_skill` (`taxonomy/repo.py:39`) uses `ilike` but does NOT call
`normalize()`. A CV with "datove modelovani" (no háčky) resolves to None even
though the canonical alias exists. `normalize()` is already written and used
by `resolve_skill_esco`. Fix: call `normalize()` on the input and add a second
query path using a normalized computed match, or store a `canonical_name_normalized`
column. The deferred item in CLAUDE.md mentions this; it will silently drop
common Czech CV phrasing from the must/nice/bridge seed-space scoring.

```
# resolve_skill path today:
"datove modelovani" → ilike("datove modelovani") → no hit → None

# after normalize() integration:
"datove modelovani" → normalize() → "datove modelovani"
                    → matches normalize("datové modelování") → hit
```

**R2 — `_personal_fit` tokenize, don't substring-contains**

`_personal_fit` (`matcher/score.py:237`) does `needle in haystack` — a raw
substring check. "SQL" will fire inside "NoSQL", "datová" won't match "data".
A single-line fix: split both to token sets and compute Jaccard overlap instead
of substring presence. Still pure Python, still O(n) — just less noisy. The
real fix (LLM scoring call) is documented as future work; the tokenized proxy
costs nothing and meaningfully reduces false positives/negatives on Czech text.

```python
# current
hits = sum(1 for needle in needles if needle and needle in haystack)

# better proxy
haystack_tokens = set(haystack.split())
hits = sum(1 for needle in needles
           if needle and (set(needle.split()) & haystack_tokens))
```

### High-value / medium effort

**R3 — Ship `perf/llm-cost` (8 → 4 calls)**

RISKS.md §LLM cost documents this precisely. The two changes are well-scoped:
1. Move `reason_for_ranking` out of `run_generic_pass` — preview cards show
   a deterministic "why it fits" summary (skill overlap count + bridge weeks),
   full reasoning fires only in `submit_role_specific`. Saves up to 3 calls.
2. Remove the redundant second `translate()` in `submit_role_specific` —
   `_personal_fit` reads `profile.summary` directly; folding the elevator pitch
   into the profile before scoring is sufficient. Saves 1 call.

Net result: 8 → 4 irreducible calls with no quality loss on the output that
matters (the recruiter-visible shortlist). This is the highest ROI deferred
item.

**R4 — ESCO vendor-tool gap (Power BI, Tableau, Excel, etc.)**

RISKS.md risk #21 flags this. ~50% of "Data Analyst" job ads require tools
not in ESCO (Power BI, Tableau, Looker, Excel advanced). Candidates who list
these get zero enrichment credit even when the skills are clearly present.
Short path: add a curated `vendor_aliases` table (30–50 rows) that maps these
common tool names to the nearest ESCO skill (e.g. "Power BI" → "data
visualisation software", ESCO id TBD). The ESCO alias loader at
`scripts/load_esco_csv.py` already handles this pattern — vendor aliases can
ride in the same seed. Negligible cost, high demo visibility.

### Architecture watch (no immediate action)

**Dual namespace tech debt** — `must_have`/`nice_to_have`/`bridge` still live
in the hand-seeded namespace while enrichment uses ESCO IDs. RISKS.md risk #20
documents this. The system works correctly as-is (seed-space is the
authoritative recruiter signal; ESCO enrichment is additive). Full unification
means moving `job_ad_skills` + `level_checklists` onto ESCO IDs, which
requires a loader rewrite + seed rebuild. Worth doing before v1 launch but not
before the demo.

**`descendants_of` BFS is Python-side** — SQLite supports recursive CTEs since
3.8.3. At prototype scale (few-hundred-node taxonomy tree) the Python BFS is
fine. If the full ESCO hierarchy is loaded (~19k edges), a `WITH RECURSIVE`
CTE would be ~10× faster and remove the Python loop. Not urgent; file when the
hierarchy query becomes a visible bottleneck.
