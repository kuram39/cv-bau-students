## Alignment with core assignment

Core assignment: AI matching platform that processes CVs (extraction of
personal data, education, work experience, skills, languages) and matches
candidates to job postings — with specific focus on students /
fresh-graduates / career-changers compared fairly against experienced hires.

### All merged PRs: ON TARGET

**Evidence quality (PRs #28, #49)** — the two highest-impact changes in this
batch. PR #28 introduced a SFIA-style evidence-strength ladder
(`source_type` → strong/medium/weak), `evidence.py`, per-skill `matched_evidence`
tags in `SkillFitDetail`, and the `doloznost_label` recruiter signal. This
replaces the LLM self-confidence band as the reliability indicator — a
principled improvement backed by research #5 (faking is the norm; demonstrated
evidence > self-report). PR #49 fixed a critical evidence misclassification:
real (non-brigáda) employment was falling to `source_type="other"` (weak) because
the `work` tier didn't exist. With PR #49 it is correctly `strong`. A backfill
script (`scripts/retag_work_evidence.py`) handles existing rows.

**Explainability / GDPR (PR #37)** — counterfactual recourse ("Doložit X →
pokrytí N%→M%") added to both the candidate panel (what to demonstrate next) and
the recruiter drill-in. No LLM, no PII — pure arithmetic from `SkillFitDetail`.
This is the GDPR/CJEU-endorsed explanation format. Also: honest-precision warning
when all matched evidence is weak (claimed-only), which is the correct way to
surface low-reliability coverage scores.

**Human oversight + audit (PR #38, #51)** — recruiter can contest any match with
a note (`set_match_override`); the override survives `rescore_ad`. Bias-audit
panel shows per-candidate-type selection rates + EEOC four-fifths ratio with a
threshold slider (PR #51). The audit is correctly framed as a disclosure metric,
not a pass/fail bar (no protected attributes in the demo). EU AI Act Art. 14 /
GDPR Art. 22 compliance groundwork is in place.

**Candidate classifier (PRs #30, #31, #33)** — classify candidate type relative
to the job ad (not just in absolute terms). Fixes the edge case where a candidate
with no real experience was mis-typed as "experienced".

**UX improvements (PRs #44, #48)** — verdict-first drill-in, bridge_fit as
concrete months-to-ready estimate. Both reduce cognitive load for the recruiter.

**Infrastructure (PRs #24, #26, #27, #29, #50)** — role-scoped seed reduces the
in-memory demo DB from ~200k to ~2k rows; Postgres compat fixes; idempotent
`_migrate_columns` prevents boot crashes on Neon when a new nullable column is
added. All correctly scoped infra work, not drift.

**Docs (PRs #32, #35, #36, #43, #46, #47)** — Czech README/ARCHITECTURE as

## Flags / concerns

### F1 — Backfill for existing deployments after PR #49

**Priority: HIGH for any live Neon/Postgres deployment**

PR #49 fixed `work` evidence tier for new candidates, but existing
`TranslatedCapabilityRow` rows in already-deployed DBs still have
`source_type="other"` for real employment. The backfill script
`scripts/retag_work_evidence.py` performs a deterministic, no-LLM retag by
matching evidence quotes against work_experience entries. If the owner has a
Neon DB with real uploaded CVs, this script must be run explicitly:

```bash
python -m scripts.retag_work_evidence          # then
python -m scripts.retag_work_evidence --rescore-ad <AD_ID>
```

The seed DB (`data/seed.sqlite.gz`) was rebaked in PR #34 — already clean.

### F2 — EU AI Act deadline: 2 August 2026 (6 weeks away)

**Priority: MEDIUM (demo context, but worth documenting)**

Research #1 established that candidate screening tools are Annex III §4a
high-risk as of 2 Aug 2026. `docs/MODEL_CARD.md` is in place. The transparency
notice is on the candidate upload screen. What's still absent from a formal
compliance checklist: (a) candidate right-to-explanation in machine-readable
form (the UI has it but there's no `/export` endpoint), (b) QMS documentation
beyond the Model Card, (c) formal conformity assessment record.

For a demo/case-study on synthetic data the risk is low, but the interview
narrative should be explicit: "designed for auditability; not a production
deployment; we know the 2 Aug 2026 deadline."

### F3 — Czech skill resolution still unmeasured (~33% baseline)

**Priority: MEDIUM — gated on running measure_resolution.py**

`scripts/measure_resolution.py` was added in PR #36 but the owner hasn't run it
yet (no results committed). Research #4 recommends `simplemma` lemmatization as
the cheapest lift before any embedding work. The current ~33% resolution rate
means ~2/3 of Czech skill phrases resolve to `None` (falling back to
explicit_skills, which are unmatched). This directly degrades student coverage
scores since their CVs are in Czech.

Concrete next step: run `measure_resolution.py`, commit the output, then decide
if `simplemma` is worth adding based on the actual gap (not the estimate).

### F4 — LLM cost: 8 calls per applicant still deferred

**Priority: HIGH (cost + latency)**

Noted in every prior review. Still not started. Each CV upload triggers ~8 LLM
calls. At Sonnet 4.6 pricing, a 100-CV demo day costs ~$2-4. The

cache translate). For a demo this is acceptable; for any real volume it's a
blocking issue.

### F5 — bridge_estimate and bridge_fit coexist (two representations)

**Priority: LOW — cosmetic, no bug**

but the DB still stores `bridge_fit` as a 0–100 abstract index. The new
`bridge_estimate` function is additive (pure derivation from `bridge_plan`), so
there's no inconsistency — but a future maintainer will see both representations
and may be confused. Consider either deprecating the numeric `bridge_fit` display
entirely (it's no longer shown in the UI) or adding a short docstring note to
`score.py` explaining the relationship.
