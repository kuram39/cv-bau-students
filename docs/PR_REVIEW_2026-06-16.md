### F1 — Dead weight constants in `config.py` (carried from previous review)

**Status: still present, misleading**

`WEIGHT_SKILL_FIT = 0.45`, `WEIGHT_BRIDGE_FIT = 0.35`, `WEIGHT_PERSONAL_FIT = 0.20`
are not imported or read anywhere since PR #20 (`total = skill_fit` directly).
The comment added in the previous review flags them as UNUSED. Still safe to
delete in a standalone cleanup PR — the comment makes it clear they are dead code,
but their presence continues to invite questions.

Same for `personal_fit=0.0` in `score.py` MatchScore assembly — a live field
set to a constant, awaiting a DB migration cycle before removal.

**Recommendation:** cleanup PR removing the three weight constants + the
`personal_fit=0.0` line. One-hour task, no functional risk.

### F2 — Rate-limit retry missing on `llm.call_json` (RISKS #4, still ⏳)

**Status: production risk, not yet addressed**

Anthropic Tier 1 = 50 RPM. A live demo with 3+ concurrent CV uploads (each
triggering 6 LLM calls) can hit this. Current behaviour: HTTP 429 propagates as
an unhandled exception → the Streamlit upload stalls with a stack trace. There
is no retry-with-backoff in `llm.py`.

**Recommendation:** Add exponential backoff in `llm.call_json` — 3 retries at
2s/4s/8s jitter, catching `anthropic.RateLimitError`. This is a
~30-line change using the SDK's built-in exception hierarchy. No test-key needed
(mock the exception). Covers the demo's most likely live failure mode before the
"thousands of ads" scale tier.

### F3 — Input truncation not applied (RISKS #10, still 🟡)

**Status: latency/context risk on long CVs**

The recruiter reasoning pass (`reason.py`) reads both the translated profile JSON
and the raw CV text. A 10-page CV can push the combined prompt to 15K+ tokens;
the chain of 6 LLM calls plus thinking blocks on a very long CV may approach the
~200K context boundary on edge cases. RISKS.md flags "truncate raw_text at ingest
to 2000 chars" as the quick fix.

**Recommendation:** In `pipeline.py` (at the point raw CV text is stored), clip
to 4000 chars with a trailing `[…truncated]` marker. 4000 chars ≈ 2 pages —
sufficient for extraction, preserves enough for the LLM to quote in reasons.
Ten-minute change.

### F4 — Multi-turn dialog for completion questions still missing (RISKS #5, ⏳)

**Status: functional gap in the two-pass pipeline**

`pipeline.py` has `ensure_role_specific_questions` and `submit_role_specific`
as distinct steps of the candidate journey. The pipeline stores unanswered
questions in the DB (`role_specific_questions`). But `ui/candidate_panel.py`
never surfaces them — candidates complete the flow without ever being prompted
for the clarifying questions the pipeline generates.

This means the "two-pass" architecture is effectively a one-pass system today.
The second pass (`submit_role_specific`) only fires when the candidate answers
questions — which they never see. The `personal_fit` score was also partly
designed to capture this; with `personal_fit=0.0`, the second pass has no effect
on the headline score even when it does run.

**Recommendation:** Candidate panel step 3 should poll `role_specific_questions`
for the uploaded candidate and present a simple st.form with one text_input per
question. Answers trigger `submit_role_specific`, then `rescore_ad`. This
activates the designed two-pass flow. Medium complexity (~1 day), high
conceptual value — it's what distinguishes this platform's architecture from a
single-shot CV scanner.
